# Measure the burst, then cut cheap delays

**Do three things in order: time each phase of a real burst, make four free fixes, then decide on two bigger levers.** The network from a home PC far from the exchange to Kalshi's servers in Ohio explains only about half of the 0.25–0.32 s between the target moment and Kalshi's stamp. A book read's round trip (a request there and the answer back) plus one order's one-way trip comes to roughly 90–145 ms. That leaves **about 0.1–0.2 s that nobody has measured yet**, so measuring comes first. The free fixes are these: send to Kalshi's recommended direct host, `external-api.kalshi.com`, with warm-ups that really reach Kalshi; read all order books in one wave; wake up on time; and plug in a network cable. Each is worth from a few milliseconds to about 100 ms. Then come the two big levers. Removing the 0.1 s spacing between orders would move orders 9–20 up by **0.1–1.2 s**. That needs either the Advanced API tier, which is permanent and a deliberate choice, or a rate-limit trick that must pass a demo test first. Running the bot on a small Amazon server in Kalshi's region, for **about $5–22 a month**, would land every order **roughly 85–120 ms sooner**. Most of these savings are estimates built from measured parts, and the table marks which is which. Swapping HTTP libraries, JSON libraries or threading styles saves a millisecond or two at most.

## Update from the bot's own log: the second book wave is the prime suspect

After the report was written, the live ledger was checked (read-only). It covers the 36 windows with orders since fast entry went live (Oct 14, 5:05 PM ET, to that evening): 117 orders.

- **Every window reads 16 order books.** 72 of 77 windows logged 16 markets. `Bot.books()` reads 8 at a time, so **every window pays a second book-read wave**, about 60–96 ms more. That's not an edge case, as the table below assumes ("only matters if a burst reads more than 8"). It happens every window.
- **The sums now roughly add up.** Two book waves (about 125–190 ms) plus one order trip one way (30–48 ms) plus a late wake-up comes to about 0.2–0.3 s. That's close to the 0.32 s median landing of each window's first order. So the "missing 0.1–0.2 s" is probably mostly the second wave. The timing log would confirm it.
- **The pacing rarely matters.** Only 2 of 36 windows sent more than 8 orders, so only 3 of 117 orders waited for the 0.1 s spacing. The Advanced tier and the bucket split (rank 6) can wait.
- **The slow tail is large.** A window's first order landed at 0.32 s at the median, but 0.85 s in the slowest 1 window in 20. Across all orders the median was 0.35 s and the slowest 1 in 20 was 1.17 s. Wi‑Fi spikes and cold connections are the likely causes. A cable and real warm-ups go after them.

**Revised order of work:** (1) the timing log; (2) read all 16 books in one wave, which means 16 threads, a connection pool of at least 16 and 16 warmed connections (the warm-up sends only 8 today); (3) the direct host with real warm-ups; (4) a cable; (5) waking on time. A server in Kalshi's region is still the biggest single lever after these.

## Free fixes rank first; pacing and a nearby server are the big levers

The table ranks each change by payoff for the cost, work and risk. "Measured" means a note timed it on this PC or read it from Kalshi's docs. "Estimated" means a note worked it out from measured parts but nobody has seen it happen in a live burst.

By raw size, the two biggest items are **removing the pacing**, which helps only the later orders, and **a server in Kalshi's region**, which helps every order. They rank lower because one needs a permanent choice or a demo test first, and the other costs money and a move. Changes 2–5 are free and small. Make them one at a time after the timing log is running, so the log shows what each one bought.

**The first step:** add a per-phase timing log to the burst code, and ship it alone. Use `time.perf_counter()` (a high-precision stopwatch) at each step, anchored to the wall clock once. Keep the times in memory and write them out after the burst ends. Turn on urllib3's debug log during the burst, so you can see any new connection opening at the wrong moment. Then collect a day or two of bursts before changing anything else. It should be written test-first and tried on a copy of `bot/`, and it needs a bot restart.

## The network explains only half of the 0.3-second delay

Kalshi's real servers sit in **Amazon's us-east-2 region in Ohio**. The host the bot uses today, `api.elections.kalshi.com`, is not Kalshi's server. It is an Amazon CloudFront edge near the caller. CloudFront is a CDN (a ring of relay servers near users), and the edge passes each request on to Ohio. All four of its addresses sit in Amazon's CloudFront range, and its replies carry that nearby edge's site tag ([network note](../research_notes/Faster%20Kalshi%20order%20sending/network_and_hosting.md); [AWS IP ranges](https://ip-ranges.amazonaws.com/ip-ranges.json)). Kalshi's docs now list `external-api.kalshi.com` as the **"Recommended base URL"** for production, and the old host as "Also supported" ([Kalshi API environments](https://docs.kalshi.com/getting_started/api_environments)). That host is a load balancer (a front door that spreads requests across servers) in Ohio, with no relay in front. A latency monitor run by Glassnode also places Kalshi's origin servers in us-east-2 ([Glassnode](https://latency.glassnode.com/prediction-markets/about)). Kalshi has never stated its region in writing.

The notes timed the trip several times, and the numbers do not fully agree. They came from **separate test runs at different times**: minutes apart on Oct 15, plus the night of Oct 11. The runs also hit different endpoints and took small samples, so some spread is expected.

| Path | Warm round trip | When measured | Source |
|---|---|---|---|
| CloudFront, order-book reads | 61–64 ms (first read 82 ms) | Oct 15, about 2:32–2:36 PM ET | [client note](../research_notes/Faster%20Kalshi%20order%20sending/python_client.md) |
| CloudFront, forced past its cache | median 82 ms (range 79–128 ms, 10 tries) | Oct 15, about 2:31–2:55 PM ET | [network note](../research_notes/Faster%20Kalshi%20order%20sending/network_and_hosting.md) |
| CloudFront, order-book reads | median 96 ms (low 84; spikes of 176 and 218) | Oct 11, night | [Oct 11 note](../research/kalshi_15min/lab/fast_entry/kalshi_api.md) |
| Direct to `external-api` | median 59.5 ms (range 57.4–60.9 ms, 10 tries) | Oct 15, about 2:31–2:55 PM ET | [network note](../research_notes/Faster%20Kalshi%20order%20sending/network_and_hosting.md) |
| Direct, bare connection only | median 93 ms (low 69; spikes of 160–210) | Oct 11, night | [Oct 11 note](../research/kalshi_15min/lab/fast_entry/kalshi_api.md) |
| A New York host, not this PC: order acknowledgment, CloudFront vs direct | median 27.3 vs 29.0 ms; worst 1 in 100: 60.5 vs 35.9 ms | late Sep 2026 | [GitHub study, now offline](https://github.com/YLiu-101/latency-expos) |

The fair reading: a warm request through CloudFront takes **about 60–96 ms** at the median, depending on the test. Direct to Ohio takes **about 60 ms** on a quiet line. The direct path was steadier in both places it was tested: its worst case was 61 ms against CloudFront's 128 ms on this PC. The New York study saw the same pattern, though its repository now returns a 404 error, so its numbers come secondhand. The Oct 11 night readings were worse on both paths, which points at jitter (how much the delay jumps around) on the home network rather than at either host.

Now the arithmetic. At the mark, the bot reads its order books, which costs one full round trip of about 60–96 ms. Then each order travels one way, about half a round trip, so 30–48 ms. Kalshi's front end adds only about 2 ms on a simple read: a warm request took 59.5 ms against a bare 57.3 ms connection ([network note](../research_notes/Faster%20Kalshi%20order%20sending/network_and_hosting.md)). That adds up to **roughly 90–145 ms of network time against a 250–320 ms delay**. Two notes worked this out separately and both found a gap: one put it at 0.1–0.2 s, the other at 150–220 ms ([network note](../research_notes/Faster%20Kalshi%20order%20sending/network_and_hosting.md); [client note](../research_notes/Faster%20Kalshi%20order%20sending/python_client.md)).

Nobody has seen inside a live burst, so the gap has many suspects. The bot might be waking late. Python 3.12's `time.time()` on Windows nominally ticks only every 15.6 ms, and `time.sleep` overshot by up to 13 ms in local tests ([client note](../research_notes/Faster%20Kalshi%20order%20sending/python_client.md)). A burst that reads more than 8 books pays an extra round trip per extra wave, because `Bot.books()` reads 8 at a time ([bot/kalshi_bot/bot.py](../bot/kalshi_bot/bot.py)). A new connection opened at the mark costs 15–40 ms to the nearby edge. CloudFront also keeps its own connections to Ohio open only "for several seconds" by default ([AWS CloudFront docs](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/RequestAndResponseBehaviorCustomOrigin.html)). If Kalshi kept that default, a quiet edge could have to reconnect to Ohio at the mark. The bot can neither see nor control that. The other suspects are signing and request-building done one thread at a time, the bot's own decision and halt checks, clock error, and queueing inside Kalshi at a busy moment.

The timing log in the first step sorts these out. It should record the planned moment and the actual wake time, the halt check, the start and end of each book read, the end of the decision, and each order's signing, sending and answer. Then add Kalshi's `ts_ms` stamp from the reply. One detail matters: the bot's current `sent` times use `time.time()`, which is the coarse clock ([bot/fast_entry.py](../bot/kalshi_bot/fast_entry.py)). Writing log lines during the burst is a trap too. One Polymarket bot builder found that synchronous logging alone cost **58 ms per order** ([casatrick, DEV](https://dev.to/casatrick/my-polymarket-trading-bot-in-rust-after-typescript-kept-missing-fills-4ena)).

The stakes are real. That same builder cut order time from **340 ms to 101 ms**, mostly by reusing open connections. Fills within half a cent of the price the bot saw rose from **61% to 89%**. That was paper trading on a different exchange by a single author, but it is the closest public match to "orders that land later fill less" ([casatrick, DEV](https://dev.to/casatrick/my-polymarket-trading-bot-in-rust-after-typescript-kept-missing-fills-4ena)). The New York study's 27 ms order acknowledgments suggest the fastest Kalshi players work in tens of milliseconds, not hundreds ([GitHub study, now offline](https://github.com/YLiu-101/latency-expos)).

## Four free fixes target the first wave of orders

**Switch hosts, and make the warm-ups real.** Today, just before the mark, the bot sends 8 cheap `/exchange/status` requests to open connections ([bot/kalshi_bot/bot.py](../bot/kalshi_bot/bot.py)). On the CloudFront host, that endpoint is cached for one second. The warm-ups are answered at the edge and **never reach Kalshi** ([network note](../research_notes/Faster%20Kalshi%20order%20sending/network_and_hosting.md)). They warm only the 5 ms hop from the home PC to the edge. On `external-api` there is no cache, so the same warm-ups open the whole path to Ohio. The catch is that Ohio's load balancer **closes idle connections after 60 seconds**. The notes measured that, and it matches Amazon's default ([AWS ALB attributes](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/edit-load-balancer-attributes.html)). Reopening a connection from home costs about **116 ms**: about 57 ms to connect plus about 59 ms for the TLS handshake (the step that sets up encryption). Through CloudFront, a new connection costs only 15–40 ms. So the switch and the warm-ups must ship together. Warm within 60 seconds of the mark, warm as many connections as threads, and use a real request, because the load balancer ignores HTTP/2 pings. The gain is **0–22 ms per round trip at the median**, depending on which CloudFront figure is typical, and up to about 65 ms on bad trips. The switch also removes CloudFront's hidden reconnects to Ohio. As a side note, the bot's comment that a cold connection costs "about 0.1-0.25 s" is too high for CloudFront, but it is about right for the direct host from home. The dashboard already uses Kalshi's direct WebSocket host ([bot/dashboard.py](../bot/kalshi_bot/web/dashboard.py)).

**Read all books in one wave.** If a burst reads more than 8 books, each extra wave adds a round trip of about 60–96 ms. The fix has three parts that go together. Use as many threads as books. Raise the connection pool size, because `requests` keeps only 10 connections per host and throws away the extras after use. Each thrown-away connection pays the full handshake again next time ([urllib3 docs](https://urllib3.readthedocs.io/en/stable/advanced-usage.html)). Then warm that many connections. The Basic read allowance holds 600 tokens, so 60 book reads fit in one go ([Kalshi rate limits](https://docs.kalshi.com/getting_started/rate_limits)).

**Wake on time.** The main loop sleeps once until a time worked out from `time.time()` ([bot/kalshi_bot/bot.py](../bot/kalshi_bot/bot.py)). On this PC, `time.sleep` usually overshot by about 0.5 ms, but the worst 1 in 100 overshot by 4.5–10.5 ms. The clock itself can be one 15.6 ms tick behind. It ticked every 2 ms in the test only because another program had sped up the system timer, and Windows 11 can drop that boost for hidden windows ([Microsoft timeBeginPeriod](https://learn.microsoft.com/en-us/windows/win32/api/timeapi/nf-timeapi-timebeginperiod)). The fix is to sleep until about 20 ms before the mark, then busy-wait: run a loop that keeps checking `perf_counter` instead of sleeping. It ties up one CPU core for about 20 ms. Moving to Python 3.13 also works, because there `time.time()` is precise to about a microsecond ([Python 3.13 What's New](https://docs.python.org/3/whatsnew/3.13.html)). But that upgrade touches every package. The expected gain is **5–10 ms, up to about 25 ms**.

**Use a cable, and keep the line quiet at the mark.** The PC is on Wi‑Fi 6E at 5 GHz. Pings to the home router averaged 9 ms but peaked at **72 ms**. Connections to Ohio had a 64.5 ms median but a **136 ms** worst case ([network note](../research_notes/Faster%20Kalshi%20order%20sending/network_and_hosting.md)). One caveat: routers often answer pings slowly on purpose, which can make those numbers look worse. Bufferbloat (extra delay from overfull queues when the line is busy) can add hundreds of milliseconds on Wi‑Fi under load ([Høiland-Jørgensen et al.](https://arxiv.org/pdf/1703.00064)). Make sure no background sync or backup uploads at the mark. A cable should barely move the median, but it should remove most of the spikes, and one spike can make a whole wave late. Nobody has measured the cable on this PC yet.

**Small items for later.** Kalshi has accepted **Ed25519** keys (a newer, faster kind of digital signature) since Sep 24, 2026, and it recommends them ([Kalshi API keys](https://docs.kalshi.com/getting_started/api_keys); [Kalshi changelog](https://docs.kalshi.com/changelog)). On this PC, signing took 493 µs with today's RSA key and 28 µs with Ed25519. Building a request took another 276 µs. The GIL (Python's rule that only one thread runs Python code at a time) makes 8 orders do this work mostly one after another. Doing it before the mark, with an Ed25519 key, gets the last order of a wave out roughly 2–5 ms sooner ([client note](../research_notes/Faster%20Kalshi%20order%20sending/python_client.md)). A new key is also a good moment to give it the narrowest permissions Kalshi allows. Everything else is noise. JSON encoding takes 1.7 µs, so orjson has nothing to save. TCP_NODELAY (a setting that stops small packets from being held back) is already on. The bot already names its shard (one of Kalshi's separate matching engines) on every order, which skips auto-routing. That is the right call, since Kalshi's only written latency statement says auto-routing "will incur an additional latency cost" ([Kalshi exchange sharding](https://docs.kalshi.com/getting_started/exchange_sharding)). HTTP/2 (a newer web protocol that carries many requests on one connection) saves about nothing over 8 warm connections ([client note](../research_notes/Faster%20Kalshi%20order%20sending/python_client.md)).

## The 0.1-second pacing costs later orders up to 1.2 seconds

The pacing exists because of Kalshi's rate limit. On the Basic tier, the write allowance refills at **100 tokens a second**, and the bucket holds only one second's worth. Each order costs 10 tokens, so **at most 10 orders can go at once** ([Kalshi rate limits](https://docs.kalshi.com/getting_started/rate_limits)). The bot sends 8 at once. It waits for their answers, then sends one every 0.1 s, and it waits for answers again after every 8 ([bot/kalshi_bot/bot.py](../bot/kalshi_bot/bot.py)). By that schedule, the 20th order leaves about **1.1–1.3 s after the first**. No network fix comes close to that for the later orders.

**Option one: the Advanced tier.** It is self-serve: one call to `POST /account/api_usage_level/upgrade`. The only condition is that at least 1 of your last 100 orders came through the API. Kalshi calls the grant **"permanent"** ([Kalshi upgrade endpoint](https://docs.kalshi.com/api-reference/account/upgrade-account-api-usage-level)). Advanced raises writes to 300 tokens a second, and its bucket holds three seconds' worth: 900 tokens, or 90 orders at once. Kalshi's pages disagree on the bucket size. One says two seconds, and an older changelog example shows a capacity of 200 tokens ([Kalshi account limits](https://docs.kalshi.com/api-reference/account/get-account-api-limits); [Kalshi changelog](https://docs.kalshi.com/changelog)). Even the smallest of those numbers fits 20 orders. After an upgrade, read the real numbers from `GET /account/limits`. The notes found no documented downside to Advanced. But it cannot be undone, so it is an option to weigh, not a step to take by default.

**Option two: the bucket split, which stays on Basic.** Kalshi bills a single order that names shard 2 only to shard 2's own bucket, and each shard's bucket "carries your full tier budget." A batch, meanwhile, is always billed to the account-wide bucket ([Kalshi rate limits](https://docs.kalshi.com/getting_started/rate_limits); [Kalshi exchange sharding](https://docs.kalshi.com/getting_started/exchange_sharding)). By those rules, the bot could fire **10 single orders on shard 2 and one batch of 10 at the same moment**, about 20 orders with no pacing. This follows from Kalshi's written rules but has never been tried, so **it needs a demo test before any live use**. If Kalshi bills it differently, the whole batch gets rejected with a "too many requests" error. That error carries no penalty or cooldown. The batch endpoint itself has been open to all tiers since Nov 20, 2025. It returns each order's own result and `ts_ms`. Kalshi does not say in what order a batch's orders reach the engine, or whether one batch can mix shards ([Kalshi batch create](https://docs.kalshi.com/api-reference/orders/batch-create-orders-v2)).

**A smaller step on Basic.** The bucket holds 10 orders, so the first wave could carry 10 instead of 8. That only works if nothing else spends write tokens just before the mark. It would move orders 9 and 10 up by roughly 0.1–0.2 s. This is an estimate from the documented bucket size.

All three options share one trade-off. The bot waits for each wave's answers on purpose, so its "three failures in a row" halt can stop the rest of the burst ([bot/kalshi_bot/bot.py](../bot/kalshi_bot/bot.py)). Sending everything at once removes that brake inside a burst. You would need to accept that, or add a different guard.

**Signature reuse is the other demo-only idea, and it is small.** Kalshi signs only the timestamp, the method and the path, not the order body ([Kalshi authenticated requests](https://docs.kalshi.com/getting_started/quick_start_authenticated_requests)). So every order sent in the same millisecond carries the same signature, and the bot could sign once ahead of time. Kalshi documents no timestamp tolerance and no replay rule (a rule that rejects a signature it has seen before), so test it on demo first. With an Ed25519 key, signing takes 28 µs anyway, and a batch needs only one signature. That makes this the least valuable item on the list.

## A server in Kalshi's region shrinks each trip to a few milliseconds

The biggest gain for every order is to stop sending it so far. An AWS server in **us-east-2** sits in the same region as Kalshi's load balancer. There, the round trip should drop from about 57–96 ms to **about 1–2 ms**, plus Kalshi's own processing. Each order would then reach Kalshi 30–40 ms sooner, and each round trip before or between orders would save 55–80 ms. In total, orders would land **roughly 85–120 ms earlier** ([network note](../research_notes/Faster%20Kalshi%20order%20sending/network_and_hosting.md)). That total is an estimate. Nobody has measured from inside that region, and **a $5 test server run for one hour would settle it**. The New York study fits the estimate: it put Kalshi's own processing at only about 6 ms, though that figure is unverified ([GitHub study, now offline](https://github.com/YLiu-101/latency-expos)). The server would also remove Wi‑Fi spikes and power or ISP outages. A cold connection there would cost only 2–3 ms, so the 60-second idle trap would barely matter.

Amazon Lightsail (Amazon's simple fixed-price servers) offers Linux plans in that region at **$5, $7 and $12 a month**, and Windows plans at **$9.50, $14 and $22** ([AWS Lightsail pricing](https://aws.amazon.com/lightsail/pricing/)). An EC2 t4g.small (Amazon's regular pay-by-the-hour servers) runs about $12 a month before disk, by an aggregator's figure ([aws-pricing.com](https://aws-pricing.com/t4g.small.html)). The clock improves too. Amazon's free Time Sync service keeps Linux servers typically within **100 µs** ([AWS Compute Blog](https://aws.amazon.com/blogs/compute/its-about-time-microsecond-accurate-clocks-on-amazon-ec2-instances/)). Compare that with this PC's drift of about 0.5 s a day. Windows servers are tuned by default only to about one second, though that can be tightened ([AWS time sync](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/configure-ec2-ntp.html)). Linux is half the price and keeps better time. But today's setup leans on Windows: scheduled tasks, PowerShell and process checks. A Windows server is the lower-effort move. A hybrid also works: move only the order-sending bot, and keep the dashboard and notifier at home. Either way, the server needs its own alerts. It also needs a key made just for it, logins allowed only from the home IP address, an encrypted disk, and no key in any git repository. Those safety steps are the note's own suggestions, not a source's.

Three other routes look tempting and are not worth it. **Chicago servers** are what hosting sellers pitch, but Kalshi is in Ohio. Even one seller's own figure puts Chicago about 10 ms from Kalshi, at $39–249 a month ([TradoxVPS](https://tradoxvps.com/best-vps-for-kalshi-trading-bots/)). A rival seller's "1 ms" claim measured a CloudFront edge, not the exchange ([QuantVPS](https://www.quantvps.com/blog/kalshi-servers-location)). **FIX** (the order protocol big trading firms use) is promised only to Premier tier and above. It shares the same rate limits as REST, has no batch message, and comes with no speed claim from Kalshi ([Kalshi FIX](https://docs.kalshi.com/fix/common-components); [Kalshi FIX connectivity](https://docs.kalshi.com/fix/connectivity)). A **WebSocket-fed order book** (a connection that stays open so Kalshi can push book changes) would skip the 60–96 ms book read from home. But it is a large rewrite. The local copy can drift: one builder saw about 1% of updates diverge, and any gap in the sequence numbers forces a full rebuild ([Dozor, DEV](https://dev.to/dozor/streaming-polymarket-and-kalshi-order-books-over-websockets-7-lessons-from-production-3khf)). Kalshi has also said that a book-format flag will change ([Kalshi WebSocket](https://docs.kalshi.com/websockets/websocket-connection)). On a server in Kalshi's region, a plain REST read costs about 2 ms, so the move would make that rewrite nearly pointless.

## Conclusion

The most useful finding is a blind spot, not a trick. Today's warm-ups are answered from a cache at the nearby edge, 5 ms away, so the bot never learns whether its path to Ohio is ready. Its own send times also come from a clock that ticks in coarse steps. Switching to the direct host and adding a precise timing log fixes both blind spots, and it turns the unexplained 0.1–0.2 s into numbers you can act on. The log also decides the next big choice. If the gap sits inside the bot (late wake-ups, extra read waves, new connections), the free fixes can close most of it from home. If it sits in the network or inside Kalshi, a server in Kalshi's region is the lever, and it makes the WebSocket rewrite unnecessary.

The two big levers fix different orders, so they don't compete. Removing the pacing rescues orders after the eighth, which now trail the first by up to a second or more. A server in Kalshi's region speeds up all of them by about a tenth of a second. Of the two, the pacing change is the cheaper one, but the Advanced route is permanent and the Basic route needs a demo test first. Both remove the mid-burst halt brake, so that choice is about how much safety to trade for speed, not just about speed.
